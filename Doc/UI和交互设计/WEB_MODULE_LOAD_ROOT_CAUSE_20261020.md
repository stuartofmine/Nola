# Web 页面加载失败：构建替换复现

## 已证实的机制

`web/frontend/vite.config.ts` 将产物直接写入正在服务的 `web/app/static/ui`，并设置 `emptyOutDir: true`。
`src/lib/pageRoutes.ts` 按需 import 页面模块，浏览器加载入口后记住这一构建的带哈希资源路径。
构建 B 清除构建 A 的资源后，仍运行 A 入口的页面再访问未加载的页面模块，会请求已删除的 A 文件并得到 404。
整页重载后拿到 B 的入口及资源路径，页面恢复。

这不是模型 API 的错误。原先 App 的 await catch 只显示通用页面错误，且没有记录失败资源，因此此前无法区分下载失败与其他模块加载错误。

## 本轮实证（00:55，隔离目录和端口 5024）

1. 用当前项目、相同 Vite/Svelte 配置构建 A 到 `/tmp/nola-load-repro/ui`；仅在测试插件中给 Chat 页面标题加入 A 标记。
2. 浏览器打开 `/settings`，加载 A 入口，未加载 Chat。
3. 构建 B 到同一目录；标题标记变为 B，使 Chat 资源哈希改变。没有注入 HTTP 失败。
4. 在原标签页点击 Nola 进入 `/chat`。
5. 服务端实际请求日志：`GET /ui/assets/Chat-DknKr3i9.js` 返回 **404**。
6. 磁盘上只有新的 `Chat-CICilEPV.js`；浏览器诊断仍引用旧的 `Chat-DknKr3i9.js`。
7. 页面显示“无法加载页面，请重试”；点击重试，页面标题变为 `Repro b 对话 — Nola`，正文与模型恢复。

截图：`/tmp/nola-web-rectify-evidence/build-replacement-failure.jpg`。
测试配置和服务脚本：`/tmp/nola-load-repro.config.mjs`、`/tmp/nola-load-repro-server.py`。
实际项目源文件和用户数据没有为复现而改写；测试构建使用临时目录。

## 结论边界与修复要求

已确认这是当前实现中可稳定触发的根因。最早那次偶发失败没有保留资源请求日志，因此不能证明所有历史失败均来自此机制。
此外，直接清空并重写正在服务的目录还存在构建过程中的短暂缺文件窗口；本轮实验验证的是构建完成后的旧入口失配，而非测量该窗口。

根治需同时处理：临时目录完整构建后发布，避免边构建边服务；已打开页面检测构建变更并在保护草稿后切换到当前构建。
仅原子替换目录不能解决旧页面的延迟 import；仅禁止缓存也不能更新已经运行在浏览器内存中的入口。
本记录完成定位，不表示发布机制已经修复，也不要求保留历史协议或旧版本兼容层。
