# 显式执行目标约束整改

对应 B05。本说明先冻结最小设计及静态自审，再修改源码；不运行编译、测试或语法检查。

## 事实与边界

Host 已不会把 attached 失败自动改为 managed；现场替换来自模型后续选择。需求范围虽绑定 accepted/applied input，现有文本 requirement 并未提供具体动作可消费的目标条件。不能从“Chrome”等词或工具名推断用户授权，也不能把错误反馈当成用户同意更换目标。

新增 Core-owned typed execution constraint ledger。第一领域为 `browser_target`，选择为精确 `attached` / `managed` 或显式 `unconstrained`。模型根据原始需求解释并记录，不由客户端改写用户提示。每份解释绑定当前 scope、已应用的真实用户输入 frontier、具体 source input 及原始模型 request/call。模型恢复、工具失败和压缩不产生新用户 frontier，不允许静默删除或改变目标。

实际新用户输入进入 scope 后，原约束继续保留；动作执行前要求模型重新解释新的 frontier，一次确认供后续调用复用。改变选择必须精确引用旧 constraint ID，并引用晚于原解释 frontier 的真实用户输入；语义是否真为用户明确改变由模型解释承担，Core 不使用关键词自称已经理解原文。新 scope 不再被视为可以自动丢弃目标的授权；只有正式 session reset 清空会话账本。

初次解释可以引用当前 scope 中已应用的交互、冻结定时、Goal continuation 或正式委派的 task input，使非交互任务不被误当作无需求；这不赋予 live user 权限。系统恢复、重放和工具错误不能作为需求来源，更不能替代已有约束。

## 具体调用的消费者

可信 Host capability metadata 声明 execution target 投影（领域、参数、默认值及 action/diagnostic 角色），Core 用已通过 schema 校验的实参解析目标。具体动作必须匹配当前约束；无登记或 frontier 待解释时产生可恢复的未执行错误。诊断 status 可读取另一后端状态，不代表已履行目标，也不取消动作约束。该元数据来自 Host schema 的结构化声明，不从工具名或用户自然语言推导。

Core 控制工具 `execution_constraints_update` 允许与动作同一模型 batch：先原子记录解释，再验证动作；不人为增加一次模型往返。控制无效则本批动作不执行。日志保留控制 call/result 和旧 ledger 项，checkpoint 保留当前 ledger，不以模型摘要恢复约束。

## 静态自审

1. `unconstrained` 必须显式记录，不把无记录等同任意替代；每个真实用户 frontier 只需一次。
2. 系统恢复、Goal continuation 和工具错误不能充当更新目标的 fresh user authority。
3. 同一输入 frontier 上更换目标或复用旧输入撤销限制均拒绝；新解释必须精确替代旧项。
4. 约束检查发生在真实动作发出前；声明与动作可同批，但错误声明不得留下部分更新。
5. 诊断只提供能力可用性事实，不能作为其他目标动作完成的证据。
6. 必须有针对故障后替换、自然追问、多语言、歧义词、冷恢复及新用户改动的回归源码；真实模型验收仍待统一测试阶段。

## 实施与待验收

Domain 新增 target selection/projection；Core 的 requirement execution state 保存有界追加 ledger（当前会话约束账本最多 128 次解释），恢复校验来源和替代关系。`execution_constraints_update` 是 Core 控制操作，可先于同批 Host 动作记录；控制失败整批不执行。调用目标 gate 位于 schema 验证之后、权限资源解析及动作派发之前，错误返回可恢复的未执行事实。CLI 内置 browser 与 chrome_native catalog 显式声明元数据，经既有 normalization 端口进入可信 capability，不向模型开放修改该字段。

回归源码覆盖缺登记拒绝、系统恢复不能改变目标、新用户 frontier 需一次确认、精确替代、默认 managed 不绕过 attached、状态诊断豁免、无约束显式登记、冷序列化及旧字段缺失拒绝。Planner 已接工具/context。跨内部续行与维护的目标约束来源成为必填 checkpoint 契约后，当前唯一 checkpoint 格式统一为 27；其他格式严格拒绝，不做转换或自动改写。此前验收不证明本次新源码通过，待所有补修收齐后统一编译复验。

模型 context 不投递 ledger 全史或 scope 全部 admissions：只保留当前 constraint 的精确 ID/选择、最多 4 个旧来源 ID、512 字 rationale 片段，以及最新真实用户输入（无真实用户输入时为初始冻结 task input）的最多 8 个完整来源 ID。源身份本身有长度预算，过预算/未投递的来源明确计数，绝不裁剪成假 ID。schema 仅在真实暴露 target-sensitive Host 工具时提供；无浏览器工具的普通回答不增加该控制工具。已有 ledger 在最终文本阶段仍提供有界 context。

尚未证明模型必然正确解释用户原文；单元契约不等于多语言真实模型验收。Core 不进行自然语言语义验证，后续用户是否明确改变目标仍由模型带来源声明承担。该机制约束声明了 target projection 的浏览器能力，不声称能识别 shell、桌面控制或任意外部 MCP 所执行的隐式浏览器替代。

## 跨 scope 继承与维护休眠补充设计及静态自审

Goal 自动续跑会创建新的 requirement scope，维护压缩则可以暂时没有用户 scope；两者均不是用户改变目标。账本新增显式当前 scope 绑定及有界原 scope 来源快照，原 entry 的 scope、input refs 和模型 source 不改写，也不把旧 Run 输入冒充当前 requirement 的输入。旧 scope 来源快照只保存来源身份，不复制原 requirement 或其完成证据；最多 128 份，来源及应用引用总数最多 4096，序列化最多 512 KiB，超预算明确拒绝而非遗忘限制。

reset requirement state 前先验证并休眠账本；当前 scope 缺失时禁止动作准入。新 scope 正式接纳输入后再绑定账本：无新真实用户输入时原解释继续有效，GoalContinuation、系统恢复及维护指令不能替代目标；当前真实用户输入必须明确引用当前旧 constraint 并完成一次重新解释。真实用户 frontier 沿来源谱系累计，未解释的用户输入不能借新 scope 被洗掉；如果先跨 scope 而未完成解释，保持未执行，等待当前 scope 的真实用户确认。模型提示只展示有界旧来源、原 scope 和当前绑定，不投递所有历史快照。checkpoint 当前格式由主代理统一升至 27，缺失新字段或旧格式明确拒绝。

静态自审重点为：scope=None 不产生行动许可；原 entry 身份不重写；冷恢复必须能用保留的 admission/application 校验每份旧来源；自动输入不能产生替代授权；实际新用户的来源只能来自当前 scope；快照预算耗尽不得清空 ledger。对应回归包括多次 Goal 续跑、维护休眠、冷序列化、篡改来源/绑定、非 live 替换拒绝和 live 明确替换。此补充源码尚待统一编译与测试，不自行运行 Cargo。
