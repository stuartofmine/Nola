#### 主代理复核到的当前代码事实

- `MacTranscriptView` 将 `dropLast()` 放入历史 LazyVStack，末条独立渲染。新增消息使同一消息跨结构容器迁移；局部 `@State` 不因相同 `.id` 自动跨容器保留。
- `MacJournalMessageTextView` 的元数据、已读引用，以及 preview 的正文/语义投影均由视图局部状态持有，重挂载前初始内容为空。
- `macChatMessageIsVisible` 只判断内联 text / presentation，未判断 journalReference；仓库投影已正确接纳 journal-only 消息，但第二次 UI 过滤可能丢掉终态消息。
- `MacMessageView` 的活动/来源覆盖集合也属局部状态；仅缓存正文不能保证重挂载时不短暂重复活动。
- `MacMessageView` 完成前不实例化 metadata 行，完成后新增至少 24pt 高度和组间距；需要稳定占位与可操作状态分离。
- 先前全部 eager 渲染导致反复切换千万字符会话 RSS 增长约 206 MiB，超过既定 64 MiB；当前混合布局约 41 MiB。不能用恢复全量 eager 的方式回避视图身份问题。

#### 聊天子阶段设计批准

依据聊天审计采用“有界消息呈现 owner + 现有 hybrid 布局”：将已读 Journal 元数据、
有界正文投影、活动覆盖和用户展开选择从短命 View 状态迁到 Transcript 生命周期
持有的 owner，身份由数据库/会话/消息/Part 确定，不以游标版本作为身份。已开始
的有效读取不随每次通知取消，通知合并为下一次目标游标；结果按 owner 和代数校验。
Journal-only 消息参与可见性，终态 metadata 保留布局占位。

### C. 设计反思（已记录，实施中发现新证据继续修订）

检验替代方案、数据竞争、长会话成本、用户操作被覆盖、编辑未保存状态、空配置/失效配置和跨平台配置语义；记录修订而非仅宣称通过。

#### 聊天子阶段反思与约束

- 否决全 eager（已出现内存回归）及全局无限正文缓存；保留历史虚拟化，并对呈现
  owner 设明确驻留上限、退出会话释放、移出有界窗口清理与字段读取上限。
- 只缓存文本不足：活动覆盖、展开与已见动画身份必须同属 owner，否则仍会重复
  trace 或重播渐显。纯鼠标悬停/复制瞬态可以留在 View。
- “永远只发布最新”会让高频通知饿死读取；允许同一身份下发布单调中间帧，再
  追上合并后的最新游标。错误保留旧帧，不无限自动重试。
- 不用 token 触发强制滚动；滚动意图仍由现有控制器唯一持有，完成不改变阅读意图。
- 拒绝只测数学策略：必须实测 canonical Journal 行连续追加、慢读取中间帧、
  新一轮发送的重挂载与展开状态、终态占位，以及原有 64 MiB RSS 门槛。

结论：聊天方案可以进入实现；模型与跨模块方案仍需各自审阅后批准。

#### 模型与工作区设计交叉审查

  identity 或 automatic；按已有 checked product-setting 契约做版本控制，不引入
  UserDefaults 镜像。模型/连接/参数保存不得改写该意图。

  解析器区分自动无候选、显式全局缺失、显式会话缺失；后两者不静默换提供商。
  正在运行的配置冻结，会话参数覆盖与模型身份选择是独立可恢复的设置。

- Settings 只读摘要订阅同一默认投影；聊天模型菜单提供本会话参数与恢复继承入口，

- System Access 统一名称，但不改变系统权限与 Core 工具授权边界；保留各数据域
  正确的事务、删除与权限行为，不为统一外观无依据重写其业务。

反思结论：不以提高 priority 伪造默认，不以 nil→first 掩盖缺失配置，不以双层隐藏
页面或自动保存所有字段回避草稿归属。通用设置框架不在方案内，只抽取有明确领域
责任和复用者的解析、草稿、呈现 owner。逐项验收沿用三份审计中的矩阵。
