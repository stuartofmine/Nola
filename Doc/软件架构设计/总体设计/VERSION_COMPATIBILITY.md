# 发布版本与兼容策略

## 受支持基线

维护者决定重新发布 1.0.0，并将此次重发作为唯一首发基线。所有 Nola 自有协议、C ABI/JNI 契约、持久化 schema 与 Store epoch 统一为 1。此前内部开发计数（包括服务协议 54、Store 83/epoch 8）不保留适配、别名、双写或数据转换。旧开发数据库遇到新程序时明确拒绝，不自动删除或重建。

应用 SemVer 与单调 build 标识发行包；每个协议/schema 的版本标识其结构和语义，不能用应用 patch 号或数据库修订次数代替。MCP、模型供应商、A2UI 等外部协议保留其标准版本，不改写为 Nola 的 1。

字符串标记同样属于版本合同：工具结果使用 `nola.tool_result.v1`，Apple Core context 内部边界使用 `__NOLA_CORE_CONTEXT_V1__`。稳定资源标识、文件名和内容修订号不是协议版本字段，不为改号而重命名用户数据路径。

## 后续发布必须遵循

- 兼容性新增应保持已有字段含义、身份约束、权限边界和默认行为；客户端只使用已协商的能力。
- 破坏性协议变化需要明确的新版本、受支持范围、版本协商与升级指引。不得通过盲目接受未知版本绕过验证。
- C ABI 与原生绑定随完整发行包一同更新，不允许任意混装；ABI 变化需要同步头文件、JNI、各端调用和边界测试。
- 已发布数据必须有明确读取或迁移支持。迁移前保存可恢复备份，使用事务和完整性检查；失败回滚并保留原始数据。不能把“升级失败”实现为清库重建。
- 迁移测试必须覆盖上一已发布格式、用户内容/身份/权限不丢失、重复运行、失败回滚、未知未来格式拒绝与降级指引。
- 软件更新 feed 必须声明准确的数据合同。当前没有数据库迁移时，不兼容的更新继续阻止安装；只有实现并验证迁移后才能放行对应路径。

## 当前实现边界

本次只有格式 1 的创建、读取与严格校验。此前开发格式明确不支持；因为尚未出现第二个受支持发布格式，本次不预置虚假的通用迁移器，也不宣称已经验证未来迁移。下一次发布若改变契约或数据格式，须先实现适配/迁移并提供实际旧版本夹具，再更新支持矩阵。

## 产品架构

现行产品不依赖独立部署 Backend。原生客户端、CLI/Web、Application Service、Store 与平台 Host 是当前架构。源码中的旧 Backend 目录不是运行、构建或发布 Nola 客户端的前提。更新分发使用 GitHub Releases 与签名 feed。
