# 网络上传与消息发送操作权限边界

## 本轮范围

外发指上传数据、发送消息或发布内容，不是普通下载、网页读取或搜索。HTTP 方法本身不是风险判断：现行搜索协议内部的 POST 不等于上传私人文件或发布消息。`web_fetch/web_search` 保持其只读检索契约，不整体改为 ExternalSend，不追加每页确认、不修改重定向和重试。输入、目标、权限及结果继续由既有 Core/Host 边界负责，不按用户措辞或 curl 等命令字符串推断效果。

## 现行工具与可达执行

CLI 内置 catalog 和实际 dispatch 没有通用 HTTP request/POST、上传文件、发送邮件或第三方消息工具。现有 `send_agent_message` 是内部已拥有子任务的协调，不是外部消息 API。`browser_upload_file` 仅有参数校验残留，没有已注册工具或可达上传 handler；native Chrome action 映射不支持上传，Mac 当前工具面也明确不暴露该 action。不能为使用 ExternalSend 枚举而把不存在的功能注册进产品。

`web_fetch/web_search` 的 schema 只允许其已声明参数；method/body/files/headers 等扩展必须在 dispatch 前拒绝。全部允许跳过 Nola 确认，不跳过 schema 和可达工具验证，也不把一个未知工具名变成可执行 HTTP 操作。新增回归覆盖当前 schema 与真实 dispatcher 的拒绝边界，不发送任何网络请求。它们证明读工具不能被扩参改成专用上传/POST 消息工具，不证明任意服务器收到 GET 一定没有副作用。

实际任意程序执行由 ProcessInvocation 的具体原始输入、cwd、Host 与现行权限链准入；不能从不透明程序推导普通读取或凭旧批准扩大执行范围。MCP 的连接和具体工具仍需分别审查可信目标/操作事实，远端自述 readOnlyHint 不是外发授权。这两项由对应实现组收口，不能把 HTTP 读工具的负例当作所有网络已被覆盖。

## ExternalSend 的适用边界

已有 `PermissionOperationRisk::ExternalSend` 继续用于可信 Host 明确提供的上传/发送操作；谨慎确认、全部允许不加另一套 Nola 审批。真正存在该 producer 时，必须绑定原完整输入与目标资源，并由同一 ExecuteTool/执行回执链承担实际交付；配置存在、enabled 或模型声明不授予许可。本轮没有新增这种 producer，也没有实现聊天渠道回复系统，不宣称覆盖不存在的专用 HTTP 功能。
