# Testing Architecture

## Purpose

Nola tests must identify which product boundary was exercised and retain
independent evidence for every claim. A test name, a real model call, or a
script-reported boolean is not sufficient evidence of end-to-end behavior.

## Current commands and coverage (2026-11-08)

| Entry | What it can establish | What it does not establish |
| --- | --- | --- |
| `cargo metadata --offline --no-deps --format-version 1` | Workspace declaration graph | Runtime purity, transitive capability use or execution correctness |
| `cargo test -p <package>` | Selected package/target tests | Tests for every extracted crate; running from core/ still does not mean the whole workspace |
| `cargo test --workspace` | Workspace targets selected by Cargo | Actual native apps/devices, real credentials or providers |
| `./scripts/test_mac_layers.sh <layer>` | Named Mac layer with Test configuration | Signed daily Debug product, unselected layers or full live UI |
| `xcrun simctl list devices available` + `./scripts/run_client_tests.sh` | Available simulator selection and declared iOS test scope | Locked physical devices or actual OS background operation |
| Android Gradle JVM / connected targets | Separately reported unit / emulator-device coverage | Native UI behavior from JVM-only tests |
| Web check / test / build | Separate static / selected behavioral / bundle checks | Browser gestures, focus, real Host and provider calls without separate execution |

Mac XCTest must use `Test` and `Products/Test`, never unsigned `Products/Debug`. Apple test runs follow the repository device guard and isolation rules. Every command reports skips and actual scope; a prior successful result is not reassigned to a newer working tree. This document update ran source/metadata/link checks, not these test suites.

## Test layers

### Module

Exercises one implementation unit without crossing a process or platform
boundary. Examples include parsers, reducers, permission policy, context
accounting, and Markdown state transitions.

### Contract

Exercises a typed boundary with controlled peers. Examples include Core/Host
events, provider payload compatibility, tool lifecycle balance, and persisted
schema invariants.

### Product runtime

Runs production runtime code across real process boundaries. It may include a
real model, Agent Host, tools, and durable storage, but it does not claim that
the user interface was exercised.

### Product UI

Drives the shipped user interface and verifies user-visible behavior. A product
UI scenario must retain visual or accessibility evidence in addition to
runtime evidence.

## Evidence rules

Real scenarios use schema 1 receipts produced by
`scripts/real_e2e_evidence.py`.

Each assertion references one or more observations. Required observations are
declared by the scenario in `scripts/real_e2e_matrix.json`.

Supported evidence includes:

- `provider_trace`: sanitized traffic recorded by the transparent provider
  probe. Real request counts are derived from successful external model
  responses, never from a script-supplied integer.
- `event_stream`: Core, Host, tool, or product event records.
- `persistence_store`: the isolated durable store used by the run.
- `persistence_audit`: an independent audit with `passed: true`.
- `runtime_receipt`: product runtime projection and lifecycle measurements.
- `ui_screenshot`: a non-empty screenshot of the exercised state.
- `accessibility_tree`: semantic UI structure captured from the product.
- `ui_timeline`: timestamped visible-state changes, such as stable bubble
  identity and progressive Markdown rendering.
- `transcript`: the ordered, user-visible messages captured from the product.
  For product persistence claims it must be generated by reopening the canonical
  Store and projecting its Messages/Parts. A test-authored array containing the
  submitted prompt and expected answer is not transcript evidence.
- `test_report`: the native XCTest/JUnit report. This proves that the selected
  test method executed, but never substitutes for provider or product evidence.
- `instrumentation_output`: the raw device/emulator instrumentation result.
- `process_log`: complete runner output when a scenario exits before its adapter reports.
- `http_transcript`: redacted request/response metadata captured across a real
  listening socket. The central judge requires the complete authenticated
  lifecycle and a unique payload read back through the public API.

Observation files are copied next to the receipt before the scenario exits.
The receipt records SHA-256 hashes, and the runner verifies the durable copies
after process cleanup.

## Prohibited false positives

- Do not label a reducer, fixture renderer, or acceptance harness as product UI.
- Do not infer streaming quality from the number of provider or Core deltas.
- Do not report real provider requests with a hard-coded count.
- Do not accept assertions without references to retained observations.
- Do not let an older assistant message satisfy the latest Turn. Persistence
  audits locate the last user position and require a later durable assistant.
- Do not compare provider traffic against second-precision run timestamps when
  trace events retain sub-second precision. The latest trace is the request
  window authority.
- Do not require `tool.started` for a call denied while waiting for permission.
  Its valid lifecycle is permission requested, permission denied, then a failed
  terminal tool record with no execution.
- Do not treat an audit exception as a product failure or success. Auditor
  fixtures cover mixed timestamp formats, latest-Turn absence, UI/database
  disagreement, duplicate terminal answers, and permission denial.
- Do not keep temporary workspaces merely to make evidence validation pass.
- Do not replace a real model or real tool boundary with fixture JSON while
  retaining an end-to-end label.
- Do not use keyword routing to make prompts pass a scenario.
- Do not reuse a cached native test result as a real execution. Real Gradle
  provider scenarios use `--rerun-tasks`; native wrappers must reject skipped
  or missing selected tests.
- Do not collect evidence only after assertions pass. Product UI scenarios must
  emit partial provider, event, persistence, transcript, timeline, accessibility,
  screenshot, and process-log evidence from a `finally`/teardown path.
- Do not place an unbounded command inside a bounded polling loop. Every ADB,
  simulator, browser, Host, and network probe has its own deadline in addition
  to the scenario deadline; an unresponsive child process must be recovered or
  terminated before retry.
- If no receipt is produced at all, the matrix runner emits a failed
  `scenario-process` receipt with the durable process log, exit code, timeout
  state, and skip markers. Required product observations remain unsatisfied.

## Streaming UI acceptance

A streaming UI test should verify all of the following:

1. The assistant placeholder appears promptly after send.
2. The same message/bubble identity remains mounted for the response.
3. Visible text advances through multiple semantic stages.
4. Markdown nodes appear during the stream, not only after completion.
5. The final rendered text agrees with the persisted assistant message.
6. Tool, thinking, cancellation, and terminal states do not duplicate or
   replace the assistant body.
7. A response above the large-response threshold has at least three semantic
   presentation mutations and more than one terminal trace body part. Provider
   chunk counts alone are insufficient.

## Terminal answer evidence chain

For one production run, all of the following must agree:

1. The provider trace contains exactly one text-bearing `stop` response and no
   later model request in the run window.
2. Core emits exactly one terminal Turn event and no later trace event.
3. The folded assistant trace body equals the latest durable assistant message.
4. The product presentation `raw_text` equals that same durable message,
   including blank lines and fenced-code delimiters.
5. Tool terminal records balance with either an executed `tool.started` event
   or an explicit pre-execution permission denial.

The canonical Part fixture is generated by Core and consumed by client
reducers. Harness source lists are part of the contract: a harness that no
longer compiles is a failed test, not skipped coverage.

## Canonical persistence acceptance

Current client persistence must exercise a fresh current-schema Store database and prove:

1. Stable user, assistant, Turn, Run, Part, and tool-call identities survive reopen.
2. Replaying the same Host cursor does not duplicate text, reasoning, tools, or terminal events.
3. A later Part update changes only that Part; it never overwrites an older message.
4. The assistant body is reconstructed from Text Parts only; reasoning and tool output remain
   structured presentation and never leak into answer text.
5. Compaction appends a context snapshot while the source transcript remains byte-for-byte intact.
6. Backup, inspector, background execution, conversation list, and chat body query the same Store.
7. Unsupported schemas and old archive formats are rejected. No old-version importer,
   converter, dual-reader, or runtime fallback exists; validation never modifies user databases.

## Current migrated scenarios

- CLI multi-tool recovery: provider trace, event streams, runtime database, and
  checkpoint evidence.
- Web real agent: Playwright product UI, provider trace, DOM timeline,
  screenshot, accessibility tree, Core events, persistence, Skill lifecycle,
  unknown-tool recovery, and cancellation.
- macOS real Agent Host product UI: shipped SwiftUI/AppKit workspace, real model,
  provider trace, tool/reasoning Parts, progressive presentation receipt,
  isolated database, persistence audit, accessibility evidence, and an opened
  render screenshot. The persistence suite also replicates remote Core Parts by
  cursor, replays duplicates, reaches terminal state, reopens SQLite, and
  compares the reconstructed transcript.
- macOS managed-browser product path: Xcode product must contain pinned Node and
  `playwright-core`; artifact E2E launches that exact runtime, while the Rust adapter E2E executes
  `browser_start → browser_snapshot → browser_screenshot → browser_stop`. A separate contract test
  proves text-only models never receive screenshot bytes and explicitly visual models receive a
  structured image block.
- Android product UI: production `MainActivity`, real provider, progressive
  Markdown timeline, terminal screenshot, instrumentation output, canonical
  Store cold-reopen, and a Store-derived ordered transcript. Device discovery,
  boot checks, ABI reads, and shutdown are individually bounded.
- iOS product UI: production chat, real Host/provider/tool call, progressive
  Markdown timeline, terminal bubble stability, screenshot, accessibility tree,
  app relaunch, and canonical restored transcript validated from XCTest and the
  xcresult bundle.
- Remote Host acceptance: owned Rust Host and isolated Store, selected real
  model, browser/mobile submission, committed Run/result and independent physical
  side-effect audit. No independent Backend is required by the current product.
- Standalone prototype replay: synthetic design states and interactions only;
  never counted as a real-model or native-client acceptance lane.

Other scenarios remain migration work until they declare required observations
and assertion evidence in the matrix.

## CLI / Web / macOS alignment gate

Run `scripts/test_cli_web_mac_alignment.sh` whenever Core Parts, Host envelopes,
permissions, goals, streaming, terminal reconciliation, or composer state
changes. The command consumes the Core-generated canonical Part fixture in the
CLI, Web production JavaScript reducer, and macOS production Swift reducer; it
also runs the CLI real PTY successor-input scenario, Web incremental UI geometry
tests, and macOS terminal/visible-run tests. This shared gate prevents three
independent green suites from validating different lifecycle layers.

Web Playwright tests use `web/tests/playwright_browser.py`; individual tests
must not hard-code a Playwright cache revision or duplicate browser launch
arguments. macOS visual tests retain reviewable PNG attachments in xcresult.
Passing reducer assertions without executable browser/native Harness evidence
is a coverage failure.
## macOS test layers

Use `scripts/test_mac_layers.sh` instead of treating every macOS test as one
undifferentiated suite:

- `contracts` is the pull-request/default loop. It covers unit, protocol,
  persistence, permission, Host, Skill, and product-path integration tests,
  while excluding screenshot-driven suites and real local-model inference.
- `visual` runs production SwiftUI/AppKit views at their supported window sizes.
- `full` is the release/nightly gate and runs every macOS test.

Tests must use ephemeral loopback ports by default. A fixed developer port is
production configuration, not test isolation. One listener collision must not
turn every Host/Skill scenario into an indistinguishable cascade of failures.

When a streaming block is mutable, tests assert both phases: the mutable tail
must be renderable before the Markdown block closes, and the same block must be
committed exactly once after closure.

## Run configuration and streaming performance evidence

The Run boundary requires transaction and runtime evidence, not timing-only
benchmarks:

- two consecutive Runs in one conversation use two different platform-supplied
  configurations without the second inheriting the first;
- an active Run resumes after process restart with its original redacted
  snapshot and digest even when platform defaults changed;
- a missing or wrong Host `config_digest` leaves sequence, effect, Part,
  checkpoint, and projection unchanged;
- credentials are absent from SQLite, checkpoints, event payloads, traces, and
  captured logs;
- a long stream proves fewer durable commits than provider deltas, bounded
  first-visible latency, stable Part identity, Markdown continuity, and exact
  terminal text;
- the hot-path test records one Core construction/restore for an uninterrupted
  Run and a new restore only after forced service restart;
- a large artifact test records bounded chunk requests and verifies that the
  raw blob is absent from checkpoint and ordinary trace payloads.

Real-provider validation retains provider trace, Run snapshot digest, semantic
batch metrics, SQLite transaction evidence, final cold-read transcript, logs,
accessibility tree, and screenshots from the same Run identity.

The current acceptance suite additionally requires split-tag reasoning streams,
unfinished Markdown blocks, duplicate events, stale recovery snapshots, and
process restart to preserve one append-only assistant projection. A client test
that only checks final text is insufficient because it cannot detect an
intermediate overwrite, duplicate render queue, or terminal tree rebuild.
