# CLI SOP、能力与长任务目标设计

## 1. 文档目的

本文定义 Nola CLI 的目标行为和改造边界，覆盖：

- 复杂任务的 SOP 与自主规划
- 工具、Skill、数据源和后台任务的统一编排
- 长任务的持久化、恢复、取消和资源预算
- 权限、上下文压缩、流式输出与终端交互
- CLI Host 与 Core 的职责边界
- 可验证的端到端验收标准

本文是目标设计。现状缺口和修复记录仍维护在
`Doc/历史任务/实施与审计/CLI_SOP_CAPABILITY_LONG_TASK_GAP_ANALYSIS.md`。

## 2. 核心原则

### 2.1 模型负责语义决策，代码负责确定性约束

模型根据用户目标、工具 schema、Skill 指令和当前上下文决定下一步行动。代码不得通过关键词、语言列表或正则表达式替代模型进行工具路由。

Core 只对已经产生的具体调用执行确定性检查：

- 工具是否存在并在当前平台可用
- 参数是否满足 schema
- 资源是否在允许范围内
- 权限是否已经授予
- 调用是否可重试、可恢复或需要确认
- 结果是否属于当前活跃调用

### 2.2 Nola 持有完整事实，UI 只投影状态

对话正文、思考事件、工具调用、权限决定、任务状态和附件引用都必须持久化为结构化事实。终端渲染不得成为唯一状态源，也不得根据当前屏幕内容反推运行状态。

### 2.3 前台轮次与后台任务是两种执行形态

普通调用留在当前轮次。只有满足以下条件之一时才提升为持久后台任务：

- 预计持续时间明显超过交互等待阈值
- 需要跨进程、跨重启或跨会话继续执行
- 需要周期性轮询外部状态
- 用户明确要求后台执行
- 子任务可独立产生可检查的中间产物

不得为了规避超时，把每个工具调用都转成后台任务。

### 2.4 稳定标识保证恰好一次语义

每个工具调用具有稳定 `call_id`，每个副作用具有稳定 `effect_id`。重放相同调用时：

- 已完成：返回原结果
- 正在运行：返回现有任务句柄或当前状态
- 已失败且可重试：基于明确策略创建新 attempt
- 未执行：执行一次

不得因为 Host 重启、UI 重连或 outbox 重放而创建第二个任务。

## 3. 分层架构

### 3.1 Core

Core 负责跨平台复用的语义与状态机：

- Turn、Call、Effect、Task、Permission 的状态转换
- 工具目录和平台能力裁剪
- 调用参数和结果契约
- 上下文预算、压缩计划和恢复协议
- 稳定标识、幂等与重放规则
- 任务生命周期和资源预算模型
- 可恢复错误与未知工具恢复

Core 不直接读取文件、访问网络、启动进程或绘制 UI。

### 3.2 CLI Host

CLI Host 负责操作系统和终端能力：

- 文件、Shell、PTY、网络和浏览器工具的实际执行
- 权限面板和用户输入挂起
- 后台子进程、进程组和取消信号
- 本地任务数据库和产物文件
- 终端尺寸、光标、滚动区域和增量渲染
- Debug 日志与可导出的会话诊断包

Host 不得重写用户 prompt，也不得通过关键词强制选择工具。

### 3.3 模型与 Skill

模型负责理解目标和选择能力。Skill 提供领域 SOP、质量标准和产物规范，但不是隐式权限，也不是字符串路由规则。

Skill 的执行应显式展开为普通工具调用，因此仍然经过同一套参数校验、权限判断、任务记录和结果持久化。

### 3.4 CLI UI

CLI UI 只消费结构化事件：

- 当前阶段与简短状态
- 思考摘要
- 工具名称、关键参数和结果摘要
- 权限请求
- 后台任务进度
- 最终回复
- 上下文使用量

UI 可折叠详情，但不能隐藏正在发生的关键步骤，也不能把调试字段直接暴露为用户文案。

## 4. 标准执行 SOP

### 4.1 接收目标

1. 保留用户原始输入，不做客户端关键词重写。
2. 合并会话级设置、工作区、长期记忆和显式附件。
3. 计算真实 token 使用量、模型总窗口和剩余预算。
4. 判断信息是否足以开始；只有不可合理推断的关键缺口才询问用户。

### 4.2 制定计划

简单任务可以直接行动。复杂任务由模型生成可调整的短计划：

- 每步必须有明确目的
- 标明依赖、可并发性和预期产物
- 预估是否需要后台执行
- 提前识别大文件、长输出和高风险副作用

计划不是固定轮次限制。任务未完成时可继续执行，直到完成、用户取消、资源预算耗尽或出现不可恢复阻塞。

### 4.3 执行与观察

每轮只向模型提供：

- 当前目标与有效计划
- 最近必要对话
- 已压缩的历史摘要
- 本轮可用工具 schema
- 已调用工具的参数与截断结果
- 活跃任务状态

进入下一轮后清空上一轮的临时工具集，不重复注入全部原始输出。完整输出保存在 artifact 或 transcript 中，需要时再按引用读取。

### 4.4 结果交付

最终回复必须区分：

- 已完成并验证的结果
- 已创建但仍在后台运行的任务
- 未验证的假设
- 失败或跳过的步骤
- 可打开的文件和产物

不得声称已经创建、修改或验证文件，除非对应工具事件已经成功持久化。

## 5. 长任务状态机

统一状态：

```text
queued -> preparing -> running -> waiting_permission
                         |            |
                         v            v
                      waiting_external
                         |
                         v
             completed | failed | cancelled
```

要求：

- `queued`：任务已持久化但尚未获得执行槽
- `preparing`：解析环境、依赖和输入，不进行不可逆副作用
- `running`：至少一个执行单元正在运行
- `waiting_permission`：流程挂起，不占用模型轮询
- `waiting_external`：等待下载、远端作业或用户外部操作
- 终态只能写入一次

每次状态改变都写入单调递增的事件序列，并记录：

- `task_id`
- `call_id`
- `attempt`
- 时间戳
- 当前阶段
- 进度和可读摘要
- 资源使用量
- 最新检查点
- 产物引用
- 错误或取消原因

## 6. 后台执行与资源预算

### 6.1 预算维度

后台任务必须支持：

- 最大墙钟时间
- 最大输出字节数
- 最大重试次数
- 最大并发子任务数
- 可选 CPU、内存和进程数量限制
- artifact 总大小限制

预算耗尽必须产生结构化终态，不能只留下被杀死的进程。

### 6.2 取消

`stop_task` 针对类型化任务执行，不允许根据 metadata 中是否出现 PID 等字段猜测任务类型。

取消流程：

1. 写入 `cancel_requested`
2. 触发对应执行器的取消令牌
3. 对进程任务取消整个进程组
4. 等待有限宽限期
5. 必要时强制终止
6. 持久化 `cancelled` 终态
7. 恢复父轮次并向模型返回取消结果

Shell、Agent、下载和远端任务必须使用各自执行器，不得互相回退。

### 6.3 重启恢复

Host 启动时：

1. 加载非终态任务
2. 根据任务类型读取检查点
3. 对可恢复任务重新连接或续跑
4. 对不可恢复的孤儿任务写入明确失败原因
5. 重建 outbox，避免重复副作用

## 7. 权限设计

推荐模式只在不可逆或明显越界操作时确认。权限范围包括：

- 单次调用
- 当前会话
- 指定资源或命令前缀
- 持久规则

规则必须匹配规范化后的具体调用，而不是 UI 展示字符串。例如 Shell 工具先解析执行结构，再对可执行文件、参数和目标路径做权限判断；不得因为展示中带有 `bash cmd=` 而导致规则失配。

`Custom response` 的语义是挂起当前流程并回到主输入框。下一条普通输入作为该权限请求的回复，不创建新的用户任务。

## 8. 上下文管理与压缩

上下文显示统一使用：

```text
上下文 34% · 21.8k/64k
```

进行中、完成后和 Debug 模式不得切换成不同口径。最大值表示模型总窗口，不是消息条数或随意推断的软限制。

压缩采用代码与 LLM 结合：

1. 代码保留系统约束、活跃计划、权限、未完成调用和最近消息。
2. LLM 总结较早的语义历史、决定、事实和未决事项。
3. 工具大输出转为引用，只保留截断摘要。
4. 压缩结果包含覆盖范围和来源消息 ID。
5. 完整 transcript 永久保留，可重建与审计。

支持自动压缩和 `/compact` 手动触发。

## 9. 终端交互与显示

### 9.1 稳定布局

- 输入行、光标和 footer 使用单一布局控制器
- 用户开始输入后，footer 从输入区域退出，不覆盖光标
- 长输出进入终端历史缓冲区，不通过反复清屏只保留最后几行
- 窗口 resize 后根据结构化块重新布局
- 流式事件只更新对应活动块，不重绘整段历史

### 9.2 工具显示

默认显示：本地化名称、关键参数、当前状态和结果摘要。例如：

```text
› 浏览目录  ~/Desktop/Nola
  找到 38 个模块和 9 种语言
```

不显示冗余的 `tool completed`，不直接显示内部 JSON envelope。Debug 模式可展开 `call_id`、耗时、完整参数、截断策略和 artifact 引用。

## 10. 与成熟 Agent CLI 的主要差距

### 10.1 SOP 仍缺少可持续纠偏

成熟实现会把计划、观察、验证和恢复作为统一循环，而不是让模型在每轮重新理解整个任务。Nola 需要让计划和未决事项成为持久状态，并用真实工具结果更新计划。

### 10.2 长任务不只是子进程

成熟实现将长任务视为有身份、有预算、有事件、有检查点的作业。Nola 已具备持久任务基础，但仍需补齐多任务竞争、公平调度、CPU/内存/进程树预算和外部服务恢复。

### 10.3 权限需要调用级规范化

权限体验不稳定通常不是面板问题，而是同一动作由不同工具或不同 Shell 包装表示。目标是统一具体能力契约，并在执行前产生规范化资源描述。

### 10.4 上下文需要可解释

上下文压缩必须能回答“保留了什么、丢弃了什么、原文在哪里”，而不仅是 token 数下降。摘要、引用和完整 transcript 应构成可追溯链路。

### 10.5 端到端验证不足

单元测试无法发现 PTY 光标、权限挂起、流式重绘、重启重放和真实模型协议问题。关键路径必须使用真实二进制、真实 PTY、持久数据库和可控的模型服务器执行。

## 11. 验收测试矩阵

### 11.1 必须覆盖的真实 PTY 场景

- 普通问答与连续多轮
- 工具成功、失败、未知工具和重试
- 权限单次允许、会话允许、拒绝和 Custom response
- ESC 取消前台轮次
- `stop_task` 取消真实流式子任务
- 墙钟预算终止挂起任务
- 输出预算正确截断 UTF-8 内容
- Host 崩溃后恢复同一任务，不重复创建
- 多个后台任务竞争执行槽且无饥饿
- `/compact` 与自动压缩
- 窗口 resize、长输出、历史滚动和输入光标
- Debug/普通模式 footer 一致

### 11.2 已获得的证据

目前已有真实 PTY 验证覆盖：

- Agent 子任务输出预算及 UTF-8 安全截断
- 墙钟预算取消真实挂起的流式子任务
- 稳定 `call_id` 重放不会创建第二个 Agent 任务
- Application outbox 与 Core pending effects 的恢复一致性

显式 `stop_task` 取消测试已暴露并修复 Agent 任务因 `runner_pid` 被误判为 Shell 任务的问题；该路径仍应以完整 PTY 回归结果作为最终关闭条件。

## 12. 分阶段实施

### P0：正确性

- 完成类型化任务取消端到端验证
- 消除重复副作用和旧 effect 重放
- 修复权限挂起与恢复
- 统一上下文 footer 口径
- 保证 ESC 和进程组取消可靠

### P1：可靠长任务

- 公平调度与多任务压力测试
- CPU、内存、输出和进程树预算
- orphan 检测和冷启动恢复
- provider/network 可恢复策略
- artifact 索引和按需读取

### P2：SOP 与能力

- 持久计划和未决事项
- Skill、数据源、工具和定时任务的统一编排
- 长任务自动提升的模型指导与确定性约束
- 验证步骤和产物质量门槛

### P3：体验与可观测性

- 终端块级增量渲染
- 后台任务中心和通知
- 可导出的 Debug session
- 上下文压缩解释视图
- 跨 CLI/Web 的一致任务投影

## 13. 完成定义

只有同时满足以下条件，CLI 的长任务能力才可视为完成：

- 真实模型能自主选择正确能力，无关键词路由
- 任务可运行数小时并跨重启恢复
- 权限决定在正确范围内稳定复用
- 用户随时能看见阶段、产物、资源和失败原因
- 用户能可靠暂停、取消和继续任务
- 上下文压缩不丢失关键决定且可追溯原文
- 重放不会产生重复文件、进程或远端副作用
- 所有关键路径均有真实 PTY E2E，而不是仅有静态断言
